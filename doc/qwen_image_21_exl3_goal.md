# Qwen Image 2.1と2.1 TurboのEXL3対応目標

設定日：2026年10月18日。現在の状態：実装中。BF16対応EXL3 Linear、校正、checkpoint、CLIの基盤を追加し、小さな実アーキテクチャでのテストを実施。[実装状況と実行手順](qwen_image_21_exl3.md)を参照。公式7Bモデルの完了条件は未達。

**Radeon AI PRO R9700単体でQwen-Image-2.1とQwen-Image-2.1-TurboのDiTをEXL3量子化し、生成・編集・RGBA出力を再現可能なCLIから実行できるようにする。** 主要Linearは4bitを出発点とし、品質に敏感な部分は高精度に残す。動作・画質・省メモリ効果を確認し、同条件のBF16と速度を比較する。

EXL3の復元コストについては[既存の調査とR9700測定](diffusion_exl3_feasibility.md)を出発点とする。合成Linearの結果を実モデルの画質や速度の保証として扱わない。

## 対象と実装方針

- モデルは公式の [Qwen-Image-2.1](https://huggingface.co/Qwen/Qwen-Image-2.1) と [Qwen-Image-2.1-Turbo](https://huggingface.co/Qwen/Qwen-Image-2.1-Turbo)。実装開始時に重みrevisionと依存ライブラリのcommitまたはversionを固定する。
- 最初の対応GPUはR9700 32GB。DiTをEXL3でGPU常駐させ、テキストエンコーダとVAEは高精度を基本とする。必要ならコンポーネント単位のoffloadやVAE tilingを使い、比較結果に設定を記録する。
- 既存のEXL3量子化・復元・HIP基盤を共用し、画像生成用のローダー、Linearアダプタ、校正、CLIを追加する。初期のモデル実行・schedulerには公式Diffusers実装を利用する。依存はオプション化する。
- BF16基準に対する数値範囲とdtypeの整合性を確認する。現状のFP16復元GEMMへの無検証なcastは完成扱いにせず、BF16対応または検証したスケーリングで解決する。
- Turboの公式カードは8-stepの保存済みsampling schedule、既定CFG=1、prefix KV cacheを説明している。単なるsteps短縮で代替せず、チェックポイントの設定を保存・復元する。通常版とTurboの校正・画質評価は個別に行う。
- 大容量の重み・校正データ・生成物は `~/datapool/` 以下へ置く。Gitにはコード、固定プロンプト、設定、コンパクトな測定結果、ドキュメントを保存する。

## 必須の完了条件

| 項目 | 確認する結果 |
|---|---|
| 実量子化 | 両モデルの主要LinearをEXL3へ変換し、層ごとのbit数・高精度保持箇所・実効bpwを記録できる |
| 保存と再読み込み | EXL3 checkpointを新しいプロセスで読み込み、変換直後と同じ設定で推論できる |
| 実行経路 | EXL3重みが実際に復元・演算に使用されていることを確認する。全DiTの高精度重みを裏で常駐させる実装を省メモリ対応として扱わない |
| 機能 | 両モデルでtext-to-image、単一画像編集、RGBA出力、2枚の参照画像による編集を実行できる |
| 解像度とメモリ | バッチ1で1024平方の基本動作を確認し、各モデルで2048平方の代表ケースをR9700単体で完走する |
| 品質 | 下記の少数固定ケースでBF16と比較し、非有限値、黒一色・ノイズだけの出力、明確な指示追従や編集・透過の破綻がないことを確認する |
| 計測 | 重み容量、ピークVRAM、denoising時間、生成全体の時間を測り、BF16との比較表を残す |
| 利用方法 | 変換・生成・編集・比較を再実行できるCLIと説明を用意する |
| 既存機能 | 共有基盤を変更した場合は、影響するLLM経路の既存スモークテストを少数実行する |

最低限の品質ケースは、各モデルにつき「写真風の生成」「文字入り画像」「構図指定の生成」「単一参照の編集」「透過画像」「2枚参照の編集」の6ケース。代表的な生成ケースの1つを2048平方とする。プロンプト、seed、参照画像、scheduler、CFG、steps、KV cache設定を固定し、各EXL3モデルを対応するBF16モデルと比較する。校正用と評価用のプロンプト・参照画像は分ける。

画像の完全一致や、BF16自体が達成できない文字精度は条件にしない。目視比較を中心に、文字や透過などケースごとの成功条件をBF16基準取得時に記録する。LPIPS等を使う場合も補助指標とし、単一の類似度だけで合否を決めない。この6ケースは実用化の初期確認であり、全入力の品質保証ではない。

## 数値目標

以下は初期の開発目標であり、現時点で達成済みの性能ではない。

| 指標 | 目標 |
|---|---|
| DiTの保存重み容量 | 元のBF16 DiTの40%以下。EXL3 payload、スケール、非量子化層を含める |
| ピークVRAM | 同条件のBF16より削減し、R9700単体で代表ケースを完走する。削減率は実測する |
| denoising時間 | 比較可能なGPU常駐条件でBF16の1.3倍以内を目指す |
| 生成全体の時間 | テキスト処理、VAE、転送を含めて報告し、offload条件の違う比較は分ける |

性能比較はモデルごとに1つの固定代表入力を使い、warmup 1回と計測3回の中央値を基本とする。初回ロード・コンパイルは別記する。両方式でresolution、steps、CFG、cache、Attention、コンパイル、offloadの条件をそろえる。BF16が同じ条件で収まらない場合はその事実を記録し、転送を含む実用比較とDiTの演算比較を区別する。

画質を保つため高精度層が増えたり、dtype対応で速度が落ちたりした場合は、容量・時間目標を満たしたと報告しない。機能完了と性能目標の達成状況を分け、未達理由と残る改善を明記する。数値目標だけのために画質や公式のsampling設定を変更しない。

## 実装の順序

1. **BF16基準と構造の確認**：両モデルのrevisionを固定し、R9700で基準ケースを生成する。Linear形状、dtype、ピークメモリ、時間内訳を取得する。
2. **EXL3 Linearと校正**：小さな実層で変換・復元・forwardを確認し、生成の初期・中間・終盤から活性値を採取する校正経路を実装する。復元作業領域はバイト数で管理する。
3. **両モデルの接続**：4bit主体のDiT checkpoint、保存・再読み込み、CLI、公式sampling設定とprefix KV cacheとの接続を実装する。
4. **品質と性能の評価**：固定ケースを比較し、必要な層のbit数を上げる。速度・容量・VRAMを報告し、再現手順を完成させる。

## 後続の拡張

V620単体・V620×2、3bit化、FP8/INT8演算、動画モデル、LoRA、HTTP APIやComfyUI連携は、この最初の完了条件には含めない。共通基盤を再利用できる構成にし、両モデルのR9700対応が成立した後に優先順位を決める。
