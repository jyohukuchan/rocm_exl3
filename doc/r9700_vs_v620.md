# R9700 と V620 の EXL3 比較

測定日: 2026-09-28。測定・監査完了。

## 比較条件

前回の [V620 Phase 2](rdna2_phase2_results.md) と同じmodel files、Python source、
Torch 2.12.0+rocm7.2、Triton 3.7.0、host HIP/ROCr 7.14を使用する。
R9700用にgfx1201 native extensionを別buildし、V620のbinaryは保持。
固定入力SHA256、batch=1、FP16 KV、context512/2048/8192、decode出力256、
chunk2048、seed1234、warmup1＋timed5、prefix cache hit=0を照合する。

- R9700: PCI0000:07:00.0、UUID GPU-a8e9ddefa2d60f55、renderD130、gfx1201。
- container: `rocm-exl3-r9700`。R9700だけを公開し、GPU試験は直列。
- V620 baseline: `/home/homelab1/datapool/rocm-exl3-rdna2/runs/{d,m}-bench-optimized.json`。
- 新しいログ: 同じartifact rootの `runs/r9700/`。
- 環境snapshot image: `rocm-exl3-phase2-env:tested`。

## 測定前に判明した実行上の問題

1. R9700既定経路の8BはPython corpusで非有限logitsになる。
   V620に入れたMLP range balanceはgfx1030限定のため適用されない。
   比較用 `r9700_balanced_run.py` で同じreview済みdevice-agnostic coreを
   deferred load後に適用した。up/downのSVHを1/8と8倍に相殺するもので、
   clipや重みfileの書換えはしない。この8B測定は完全な既定設定ではない。
   変更は固定のnon-LoRA比較用adapterであり、全モデルへのR9700一般対応ではない。
2. R9700の実機 `shared_memory_per_block` / `shared_memory_per_multiprocessor` は65536。
   forkのgfx1201設定92160のままではMのbulkが
   `coop_autotune.cu:317` のshared-memory attribute設定でinvalid argumentとなった。
   `setup.py` と `hipcc_probe.sh` のgfx1201だけを65536へ合わせて再buildした。
3. LDS修正後、M bulkはGPU exceptionになった。cooperative GEMMも
   `rdna_wmma::mma_sync` のgfx1201 trapを呼ぶことをコードで確認した。
   既存コメントの「このwrapperにはfused MoEしか到達しない」は現行GEMM実装に
   当てはまらない。比較adapter `r9700_moe_dq_run.py` で非decode forward中だけ
   `TEMP_ROWS_GRAPH=0` にし、全expertを既存C++ reconstruct+hgemm経路へ送る。
   bsz<=MAX_BSZNのmgemv decodeは変えず、終了時に閾値を復元する。
   このadapterは逐次・単一process測定用で、thread-safeな一般修正ではない。
4. V620用GQA decode tuneはgfx1030限定なのでR9700では無効。
   RDNA4では既存forkのMoE fused-mode無効化も入る。
   この比較は各GPUで利用可能な実装を含めたE2E比較で、純粋なhardware性能比ではない。

## 精度・性能

最終64KiB binaryで8ケース1024位置を確認した。

| 比較 | 8B 4bpw | 30B-A3B 3bpw |
|---|---:|---:|
| R9700 bulk vs BF16 source | 969/1024 (94.63%) | 933/1024 (91.11%) |
| R9700 decode vs BF16 source | 971/1024 (94.82%) | 937/1024 (91.50%) |
| R9700 decode vs V620 decode | 1023/1024 (99.90%) | 1014/1024 (99.02%) |

全位置有限。両モデルとも8192入力＋256-token生成で全256 forwardの有限logits、
cache hitなし、指定出力長、通常終了を別試験で確認した。この毎forward同期する
品質試験は速度値に使わない。GPU間の生成token列の完全一致は要求していない。

### 起動上の問題を回避した構成（alignment hint追加前）

速度はtok/s、warmup1＋timed5の中央値。前回の最適化済みV620との比較。

| モデル | 入力 | prefill V620→R9700 | 比率 | decode V620→R9700 | 比率 |
|---|---:|---:|---:|---:|---:|
| 8B 4bpw | 512 | 1131.3 → 4881.6 | 4.31× | 58.5 → 45.0 | 0.77× |
| 8B 4bpw | 2048 | 1155.3 → 6117.6 | 5.30× | 57.6 → 44.9 | 0.78× |
| 8B 4bpw | 8192 | 906.2 → 5242.8 | 5.79× | 47.8 → 25.3 | 0.53× |
| 30B-A3B 3bpw | 512 | 471.5 → 864.4 | 1.83× | 70.6 → 59.1 | 0.84× |
| 30B-A3B 3bpw | 2048 | 967.9 → 1943.5 | 2.01× | 69.2 → 59.1 | 0.85× |
| 30B-A3B 3bpw | 8192 | 742.5 → 1861.6 | 2.51× | 56.9 → 35.3 | 0.62× |

全72 jobsが指定長・cache miss・正常終了を満たし、入力SHA256はV620と全件一致。
ただしspreadはD decode512=13.4%、M prefill8192=15.7%、M decode2048=5.2%。
全反復を保持し、ばらつきのある群は最良値を選ばず中央値と併記する。

### Alignment hintだけを揃えた追加比較

`r9700_alignment_only.py` は既存のpointer alignment検査をそのまま使い、
gfx1201でAOT signatureの`:16` hintを有効にする。R9700の16-row tile、
split設定、warp数は維持し、V620用の4/8-row縮小は持ち込まない。
元の結果は保持したまま、この1要因を追加して切り分ける。

速度はtok/s、256-token decode、warmup1＋timed5の中央値。

| モデル | 入力 | prefill V620→R9700 | 比率 | decode V620→R9700 | 比率 |
|---|---:|---:|---:|---:|---:|
| 8B 4bpw | 512 | 1131.3 → 4795.6 | 4.24× | 58.5 → 73.7 | 1.26× |
| 8B 4bpw | 2048 | 1155.3 → 6157.6 | 5.33× | 57.6 → 73.1 | 1.27× |
| 8B 4bpw | 8192 | 906.2 → 5209.8 | 5.75× | 47.8 → 64.2 | 1.34× |
| 30B-A3B 3bpw | 512 | 471.5 → 855.1 | 1.81× | 70.6 → 99.3 | 1.41× |
| 30B-A3B 3bpw | 2048 | 967.9 → 1942.4 | 2.01× | 69.2 → 98.4 | 1.42× |
| 30B-A3B 3bpw | 8192 | 742.5 → 1853.7 | 2.50× | 56.9 → 86.9 | 1.53× |

hint追加前後のtop-1はD/Mとも1024/1024で一致。
両モデルの8K＋256生成も再度全logits有限・通常終了を確認。
正式72 jobsすべてでV620およびR9700 hint追加前との対応入力hashが一致し、
指定token数、cache hit=0、decodeごとの255 ITL、各groupの1275 ITLを確認。

hintだけの同一入力8K/64出力/2反復A/Bでは、
D decode24.96→63.58、M34.93→85.39 tok/s。
タイル・split・warpを変えずに改善したため、R9700がhint追加前に遅かった
一因をAOT alignment情報の欠落に切り分けられる。GPU traceの時間割合ではない。

正式測定の一部には単発遅延がある（D prefill512=88.6%、decode512=7.9%、
M prefill512=11.2%、prefill8192=11.8%、decode2048=12.4%のspread）。
これらは全反復を残し、該当contextを同じ入力で追加5回測定した。

追加5回の結果（主表の反復は置換しない）:

| モデル | 入力 | prefill中央値 / spread | decode中央値 / spread |
|---|---:|---:|---:|
| 8B 4bpw | 512 | 4923.2 / 2.4% | 74.9 / 1.9% |
| 30B-A3B 3bpw | 512 | 835.5 / 58.9% | 99.1 / 0.6% |
| 30B-A3B 3bpw | 2048 | 1938.3 / 0.9% | 98.2 / 9.6% |
| 30B-A3B 3bpw | 8192 | 1851.4 / 9.5% | 86.9 / 7.0% |

中央値は再現する一方、Mの一部ではspread>5%が再測定でも残った。
例としてM8K prefillの遅い反復は、hint追加前の2回目、追加後の4回目と
同一入力列の別位置に出ており、特定入力だけが原因とは断定できない。
clock/温度/電力を記録したが単発遅延の原因は未特定。各runの生ITL、最小・最大値も
保存している。ここでの結論はwarm中央値の比較で、最大レイテンシの保証ではない。
追加測定だけからhintのprefill改善を主張しない（hintはdecode限定）。


## 結論

2K/8K入力では、alignment hintを揃えたR9700のprefillはV620の約2.0–5.8倍、
decodeは約1.27–1.53倍。「prefillで大きな差、decodeでは相対的に小さい差」という
仮説と整合する。ただしhint追加前のR9700 decodeは最適化済みV620より遅く、
GPUの仕様だけでは現行forkの速度を予測できなかった。

R9700のnative小GEMM/融合MoEを実装した比較ではない。今回のM prefillは既存
reconstruct+hgemmによる回避経路で、hardwareの理論性能比・最大性能を示さない。
DのMLP対策とMoE prefill回避策、alignment比較は外部adapterとして保存し、
ライブラリの既定動作へは取り込んでいない。gfx1201のLDS設定のみ恒久修正した。

## 仮説の解釈

AMD公称メモリ帯域はR9700が640 GB/s、V620が512 GB/s（1.25倍）。
R9700はFP16 matrix演算を備え、V620移植ではSIMT/fdot2のmatrix primitiveを使う。
したがって、行列演算が支配的なprefillで差が大きく、重み読み出しが支配的な
batch1 decodeで差が小さくなるという仮説には根拠がある。
ただしEXL3復号、KV attention、host launch、MoE dispatch、cacheの差が入るため、
公称帯域比をE2E速度比の保証や上限とは扱わない。
